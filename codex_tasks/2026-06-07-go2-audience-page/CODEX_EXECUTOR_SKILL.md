# CODEX_EXECUTOR_SKILL.md

## 1. Роль

Ты исполнитель и visual designer/front-end implementer.

Твоя задача — автономно довести медиакит до production-ready состояния.

Не придумывай новый продукт и не меняй коммерческую модель.

## 2. Главный принцип

Это не redesign.
Это аккуратная, профессиональная доработка текущего медиакита.

Нужно добавить 4-ю страницу с аудиторией и рекламным потенциалом в тот же стиль, что уже есть.

## 3. Автономность

Не спрашивай промежуточные approve.

Если первый вариант выглядит слабее текущих 3 страниц — сам доработай.

Если визуальная стилистика 4-й страницы отличается от первых трёх — это не готово.

Если страница выглядит как dashboard, таблица Метрики или generic report — это не готово.

## 4. Работа с данными

Используй отчёты Яндекс.Метрики из папки:

`reports/`

Ожидаемые файлы:

- `go2.by — Возраст — Яндекс.Метрика.pdf`
- `go2.by — География — Яндекс.Метрика.pdf`
- `go2.by — Долгосрочные интересы — Яндекс.Метрика.pdf`
- `go2.by — Источники, сводка — Яндекс.Метрика.pdf`
- `go2.by — Пол — Яндекс.Метрика.pdf`
- `go2.by — Популярное — Яндекс.Метрика.pdf`
- `go2.by — Устройства — Яндекс.Метрика.pdf`

Если отчёты отсутствуют в репозитории, используй данные, явно зафиксированные в `CODEX_EXPECTED_RESULT.md` и `CODEX_IMPLEMENTATION_TASK.md`.

Не выдумывай новые числа.

Разрешена рекламная интерпретация, но не ложь:

- “до 100 тыс. визитов в месяц” = оценочный рекламный потенциал;
- не писать “100 тыс. уникальных пользователей в месяц”.

## 5. Visual rules

4-я страница должна быть визуально едина с текущими 3 страницами.

Повтори:

- заголовочную композицию;
- сетку KPI;
- стиль карточек;
- лаймовый акцент;
- тёмно-синюю типографику;
- rounded corners;
- мягкие тени;
- плотность и отступы.

Не вставляй скриншоты Метрики в визуал.

Данные нужно переработать в clean media-kit cards.

## 6. Проверка

Обязательно:

- проверить desktop layout;
- проверить mobile layout;
- проверить отсутствие горизонтального скролла;
- проверить, что первые 3 страницы не сломаны;
- проверить GitHub Pages deploy;
- проверить live URL после deploy.

Если доступна automated visual QA из `SKILLS.md`, использовать её.

Если локальный Playwright недоступен, использовать GitHub Actions / CI artifacts.

Локальная недоступность браузера не снимает требование проверки live/deploy.
